# 新建邮件组件规范

本规范仅用于把设计稿、截图或明确版式需求制作成可复用的 Freshine 邮件 HTML 组件。对既有组件做局部文案、颜色或图片替换时，遵循用户指定的最小改动范围，不将本规范当作重构授权。

## 先确定边界，再开始实现

1. 先检查当前 `组件清单.json`、现有相似组件、编辑器字段契约和用户提供的设计稿；`组件清单.json` 是组件路径和注册状态的单一事实来源。
2. 设计稿未明确组件中文名、分类、componentKey、标题/无标题变体、可编辑字段，或默认图片来源时，先在对话中列出命名、字段和同步范围并等待确认。
3. 标题版与无标题版是两个组件：使用单独目录和 componentKey；无标题版从内容 Schema、默认快照、模板和编辑器字段中移除标题字段与对应空白，不以隐藏标志代替。
4. 除用户明确要求的范围外，不修改既有组件、Campaign 组合顺序、Shopify 数据或 Omnisend 草稿。组件在编辑器中可自由加入、重复和排序，不得假定固定槽位。

## 视觉与邮件 HTML 实现

- 以 600px 桌面画布和 375px 移动目标复现设计稿。先从原图测量内容宽度、留白、列数、图片比例、字体层级与链接区；图片不得拉伸变形。
- 使用单个根 table、嵌套 `table` / `tr` / `td`、`img`、`a`、`span` 和 inline CSS。禁止 JavaScript、iframe、表单、事件属性、外部 CSS、Flex、Grid、绝对/固定定位、客户端产品加载和跨组件选择器。
- 高度还原以实际 `效果演示.html` 和编辑器预览为依据；HTTP 可用或源码存在不构成视觉验收证据。

### 统一标题、副标题与图片标题规范

仅“活动商品组件”分类中的组件必须采用以下默认值，适用于新建组件与已统一迁移的组件；用户明确提出特殊要求时才覆盖，不因复制旧模板或旧设计稿的 Medium/灰色样式而回退。头图及其他非活动商品分类组件完全排除，不修改其字体、样式、默认设置或演示。

| 层级 | 字体 | 字重 | 字号 | 行高 | 字间距 | 对齐 | 默认色 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 主标题 | Lora | Regular，font-weight:400 | 30px | 38px | 0px | 居中 | 保留组件标题色 |
| 副标题 | Montserrat | Medium，500 | 18px | 150%（27px） | 0px | 居中 | #000000 |
| 图片下标题/商品名 | Montserrat | Medium，500 | 16px | 20px | 0px | 左对齐 | 保留组件商品名色 |

- 用户描述的字重名称与数值冲突时，以明确数值为准：本次主标题 400，不能写为 500。
- 该规范仅覆盖组件清单中分类为“活动商品组件”的对应文字层级；导航、赠品与权益、测量、地址、评论、小样-产品等其他分类保留原组件样式。图片下的链接商品名即使字段命名为 cta.text，仍按商品名处理；真实 CTA、价格、折扣标签、评论正文及评论标题不套用。纯整图内的文字不拆改。
- 按 [typography-roles.v1.json](typography-roles.v1.json) 识别现有组件对应字段；新活动商品组件登记时同步扩充该清单。未列出的新活动商品组件也必须遵守本规范，清单不是豁免名单。
- 600px 按表格值，375px 按 62.5% 等比缩放；模板、默认设置/Schema、演示、管理文档和默认组合快照同步。保留原有下划线、链接、Shopify 导入字段及组件颜色编辑能力。

### 600px → 375px 等比移动端制造规范

- 所有组件以 600px 为视觉基准，375px 时受控尺寸按 62.5% 等比收缩，保持已经确认的列数、图片比例、链接边界、文案与颜色；不因移动端自动改成单列。
- 每个受控的桌面像素值必须先保留固定值，再紧跟同属性的 inline `min()` 覆写。例如 `font-size:Npx;font-size:min(Npx,N/6vw)`；`line-height`、固定 `width` / `height`、`padding`、`margin` 与 `border-radius` 均按同一规则处理。负边距使用 `max(-Npx,-N/6vw)`。
- 同一组件不得出现图片已经缩小、而字体、行高、卡片尺寸、按钮尺寸或留白仍为固定桌面像素的混合状态。`component.template.v1.html` 和 `效果演示.html` 必须同步使用相同的移动规则。
- 不缩放百分比尺寸、`auto`、`0`、`font-size:0` 占位符、1px 描边/分隔线，以及已通过 `width:100%;height:auto` 流式保持比例的纯整图。不要为满足规则而把这些例外写成无意义的 `min()`。
- 不支持 `min()` 的客户端会保留前置的桌面 CSS 回退；这不等同于 Gmail、Outlook、Apple Mail 或 Omnisend 收件箱实测。提交前必须分别说明本地静态/预览验证与真实收件箱验证边界。
- 新建或修改版式后运行 `node scripts/normalize-inline-mobile-dimensions.mjs --check` 与 `node --test tests/mobile-proportional-contract.test.mjs`。前者检查全部已登记模板与演示文件，后者禁止未来组件遗漏等比覆写。

## 图片、链接与默认素材

- 默认素材来自用户提供的设计稿时，先取得裁切或使用授权；将每个可替换图块保存为组件目录下的本地素材，并在 fixture 中以 `asset://` 和 `localReferenceAssets` 声明。
- `asset://` 仅供本地预览。导出 HTML 或上传 Omnisend 前，所有图片替换为公开 HTTPS URL；不得将本地、相对、`file://` 或 `data:` 图片带入最终邮件。
- 设计稿有多个独立跳转时，使用独立图片或表格切片，并为每个图块提供 URL、Alt 和独立点击链接。单张未切分长图只能提供一个稳定链接，不得承诺任意坐标叠加多链接。
- 图片和 CTA 的 Alt、链接目标以及可读文字必须对应实际内容；不得为纯视觉还原而删除可访问文本或错误复用链接。

## 内容契约与编辑器登记

每个新组件必须在同一次变更中同步以下内容：

1. 组件目录：`component.template.v1.html`、`component.styles.v1.css`、内容/设置 Schema、fixture/defaults、中文管理说明、真实 `效果演示.html` 和所需本地素材。
2. `组件清单.json`：中文名、分类、componentKey、600px 输出宽度、375px 断点及全部七个文件路径。
3. `editor/public/editor-ui-contract.mjs`：`editableByComponent` 白名单和每个可编辑字段的 `copyByField` 或组件级说明。白名单中的字段必须同时出现在 Schema 和默认快照；不开放未验证的几何开关。
4. `组件索引.md` 与 `references/component-interactions.zh-CN.md`：说明组件入口、可编辑项、固定版式、桌面/移动尺寸和图片链接边界。
5. 回归测试：验证注册表、目录文件、Schema/fixture、编辑器字段、邮件安全 HTML、默认素材、本地预览和实际 600px / 375px 几何。

## 验证与交付边界

在报告完成前，按此顺序获取新证据：

1. 先写聚焦失败测试，确认因新组件缺失或新约束不满足而失败；再实现最小同步变更并确认测试转绿。
2. 运行 `node --test tests/*.test.mjs`、`node skills/build-omnisend-campaign-draft/scripts/validate-campaign-contracts.mjs` 与 `git diff --check`。
3. 在本地 HTML 编辑器中添加该组件，检查 600px 和 375px 预览、默认素材加载、可编辑字段、独立链接和控制台错误；对照 `效果演示.html` 记录任何有意偏差。
4. 明确区分静态校验、本地预览、Omnisend 预览与真实收件箱测试。未进行 Gmail、Outlook、Apple Mail 测试时，不得声明“Omnisend 可发布”或收件箱像素一致。

新组件制作本身不授权任何外部写入：不得发送、排期、发布 Omnisend Campaign，也不得上传图片、创建或更新 Omnisend Draft，除非用户在当前请求中明确授权并完成现有最终确认流程。
