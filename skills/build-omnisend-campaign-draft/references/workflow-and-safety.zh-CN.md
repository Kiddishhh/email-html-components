# 当前工作流与安全契约

## 状态流

`编辑中 → 保存完成 → 检查 600px/375px 预览 → 逐组件确认（全部确认后草稿已确认） → 绑定输出 HTML 哈希 → 处理本地图片 → 导出 HTML 或写入 Omnisend Draft → 回读验证 → 关闭时清理运行数据`

保存失败时保留待保存修改，状态栏展示失败原因与重试入口；确认、结构修改、商品导入和输出依赖保存成功。API 修改请求串行执行，新输入不能被旧响应覆盖。关闭时清理运行数据；不得跳过组件确认或输出 HTML 哈希校验。

## 项目草稿与注册

- `组件清单.json` 是组件路径和注册状态的单一事实来源。每次启动前运行 `scripts/validate-campaign-contracts.mjs`。
- 校验必须覆盖注册表路径、模板、内容/设置 Schema、fixture/defaults、管理说明、组件 CSS、`效果演示.html` 和编辑器字段契约。
- 当前运行草稿保存组件成员、顺序、完整内容/设置快照、Campaign 元数据、确认状态和内容哈希；不跨服务运行持久化。
- 不保存 Shopify CLI 会话、Omnisend API Key 或其他访问令牌。
- 仅用户手动保存的模板跨服务运行持久化；普通草稿、预览、上传回执、图片缓存和导出中间文件在关闭编辑器时清理。

## 本地图片与预览

- 本地图片以 `asset://` 加资产清单的形式进入草稿，只用于本地预览。
- `--preview-local-assets` 必须相对生成的 `previewOutput` HTML 解析本地资源，并验证文件存在。
- 手动保存模板时，将本地上传图片复制为模板专属文件；覆盖或删除模板时仅替换或删除这些专属文件，绝不删除组件目录中的素材。
- 最终 HTML 不得包含 `asset://`、本地绝对路径或相对图片路径；所有图片必须是公开 HTTPS URL。
- 本地预览和截图属于验收证据，不等于 Omnisend、Gmail、Outlook 或 Apple Mail 的真实收件箱验证。

## 最终确认

当前编辑器逐个确认组件；全部确认后草稿自动标记为已确认，不另设整封确认按钮。用户应先检查完整 600px/375px 预览。上传对话框收集 Campaign 名称、Subject、Preheader；发送者及受众继续由既有 Draft/Brand 流程处理。

- Campaign 名称用于内部识别和管理。
- Subject 是收件箱显示的邮件主题。
- Preheader 是主题旁或下方的预览摘要。
- 最终确认绑定完整 HTML 的 SHA-256 内容哈希；任何内容、设置、图片或顺序变化都会使确认失效。

## 导出 HTML 边界

“导出 Omnisend HTML”仅上传本地图片、替换 URL、执行静态安全校验并复制 HTML。它不会创建、更新或发送 Campaign 或 Draft，也不保存完整 HTML、API Key 或导出正文回执。

首次 API 请求前，待上传 HTML 必须通过共用安全校验（允许合法 `asset://` 引用）；图片替换后的最终 HTML 再校验，图片只接受绝对 HTTPS 地址。图片上传前必须通过 MIME、扩展名、文件大小和本地路径检查；任一图片失败即停止。图片缓存只保存图片哈希、账户隔离哈希、Omnisend 图片 ID 和公开 URL，由默认导出适配器透传并仅在当前编辑器运行期复用；同账户同字节图片跨草稿复用，不同账户隔离。

## Omnisend Draft 写入

1. 只调用固定的 `scripts/upload-omnisend-draft.mjs`；不得手工拼接 Omnisend 写请求。
2. API Key 由编辑器对话框一次性收集，只保留在当前请求和本机进程内存，完成、失败或取消后清空。
3. 先按 Campaign 名称精确查询 `draft`；多个同名结果选择最近更新的一封。
4. 更新现有 Draft 时，先回读完整 Email Content，保留 `generalSettings`、sections、节点 ID 和 `[[unsubscribe_link]]`，只替换目标 HTML 正文后执行完整 `PUT`。
5. 没有同名 Draft 时才读取 Brand senderName、导入 HTML 并创建新的 Draft。
6. 两条路径都必须回读并验证 `status: draft`、Campaign ID、Email Content ID、退订令牌，并对实际 HTML 正文执行语义校验：规范化可见文字及顺序一致，预期公开 URL 和图片 Alt 均保留。更新仅取被替换的 HTML 区块；新建允许按文档顺序拼接平台拆分的 HTML 区块，不在整个响应 JSON 中搜索文字来代替正文验证。
7. 任一步失败都不得继续后续写入；当前草稿仅保留到编辑器关闭。

不得发送、排期、发布或调用任何使 Campaign 离开 `draft` 状态的端点。

正文来源与更新目标共用同一布局遍历，只接受 `sections[].rows[].columns[].blocks[]` 中的真实 HTML 块：`type: "htmlCode"` 的 `htmlCode.body`，或兼容的字符串 `htmlCode`（type 缺省、html 或 htmlCode）。其他块类型及任意层级 metadata 内的同名字段不作为正文，也不能成为更新目标。更新/只读恢复要求真实 HTML 块中恰有一个包含退订令牌；更新保留其 style、节点 ID、其他区块和元数据。新建回读仍允许按布局顺序拼接多个真实 HTML 块；仅响应完全没有 sections 字段时兼容旧版顶层字符串 htmlCode，不能用它绕过空的或格式错误的 sections。

回执中的 `htmlSha256`、`remoteHtmlSha256`、`readbackContentSha256` 分别描述本地最终 HTML、远端实际 HTML 和完整回读响应；`visibleTextSha256` 记录经比较一致的普通邮件分支规范化文字，Outlook 分支文字另行比较。不同对象的哈希不作为字节相同的证明；提取规则升级后的文字哈希也不保证与旧回执相同。只有正文语义校验完成后才返回 `readbackVerified:true`；回读失败不自动重试写入，不保证已接受的远端写入被撤销。该验证不替代布局、字体、颜色或真实收件箱检查。

## 编辑器链接与 UTM 边界

- 清单来自当前草稿实际生成的链接，包含固定退订链接。固定链接只读，不修改组件模板。
- 批量 UTM 仅修改用户勾选且由字段白名单开放的 HTTPS 链接，先展示差异，再应用。
- 保留原有非 UTM 参数和片段；空白 UTM 输入不清除原值；mailto、tel、退订令牌及图片源不参与修改。
- 修改使对应组件及整封确认失效；失败修改保留在队列，重试成功后重新确认。
- 缩略图 iframe、搜索、分组、链接表和编辑器界面的样式仅用于本机界面，绝不拼接进正式邮件 HTML。

## 文案样式边界

- `textStyles` 是实例和文案字段级的受限覆盖，不改变组件默认模板。真实文本节点才允许设置，图片、Alt 和 URL 不接受样式；API 和构建器都校验字段与值。
- 样式通过原保存队列、模板和 Composition 进入邮件内联 CSS；不引入外部字体、运行时样式脚本或任意 CSS 输入。恢复默认同样使确认失效。
- 保留链接、UTM、独立分隔行、左右 padding 及非目标文案。行内对齐使用独占字段的布局容器，不能修改多个文案共享的行来影响其他字段。
- 规则与尺寸范围见[文案独立样式](text-style-controls.zh-CN.md)；移动浏览器验证不等于真实邮件客户端证明。

## 静态邮件安全

- 邮件 HTML 不得包含 JavaScript、iframe、表单、事件处理器或运行时 Shopify 请求。
- 组件使用邮件安全表格结构与内联 CSS；不得依赖 Flex、Grid、外部样式表或 Web Font 才能完成核心布局。
- URL 字段按 Schema 校验；正式图片地址必须使用 HTTPS，即使 Schema 未声明 `protocol` 也不接受 mailto/tel 或相对图片地址。mailto/tel 只用于链接。
- `safe-email-html.mjs` 同时验证普通邮件分支与 Outlook VML 分支：标签必须正确闭合，拒绝事件属性、重复属性、异常注释、脚本、未解析组件占位符及危险 CSS。CSS 的 URL 也必须安全，不支持 `image-set()` 等额外图片语法或无法识别的命名实体。
- 本地预览只豁免由素材表实际解析出的图片路径；不能用预览模式放行模板内任意相对图片。校验不改写输出，合法 VML、inline min/max 尺寸与原有链接保留。
- 组件 CSS 只内联到当前组件，不得改变其他组件。
- 保留退订令牌 `[[unsubscribe_link]]`。

## Shopify 边界

只有执行组件的 Shopify 导入时才读取 `shopify-data-contract.zh-CN.md`。所有 Shopify 操作严格只读；不创建、修改、上传、发布或删除任何店铺数据或主题。


## 实体回读、素材引用和模板复用边界

- 回读比较对正文、Alt 和 URL 实体执行单次解码，支持 HTML5 命名实体、十进制/十六进制数值实体及 Unicode。`&amp;` 与 `&#38;`、`&nbsp;` 与 `&#160;` 等价时不误报；字面文本 `&amp;#38;` 只解码为 `&#38;`，不能再解码成 `&`。真实文案变化仍必须报错。规则参见 [HTML 字符引用](https://html.spec.whatwg.org/multipage/named-characters.html)；固定查找表来自 Python 标准库 `html.entities.html5`，保存在 `html-named-entities.v1.json`，运行时只需 Node.js，无联网查询或 Python 依赖。
- 正文提取和节点校验共用 `readback-html-tokens.mjs` 的标签分词：单引号或双引号属性中的 `>` 不结束标签。`alt="Room > garden"` 与 `alt="Room &gt; garden"`（或十进制/十六进制形式）双向等价；属性内容不能泄漏成可见正文，真实 Alt 和正文变化仍报错。
- 本地图片全部取得上传/缓存 URL 后，按原 HTML 中的完整 `asset://<id>` token 一次性替换。前缀相同的 ID（如 `benefits-strip-4` 与 `benefits-strip-4-two-rows`）必须分别对应自己的图片；同一 token 在 img、background、CSS、VML 中重复出现也一致替换。替换值按普通字符串处理，不解释 `$&` 等 JavaScript 替换语法。
- 从模板复制图片时，目标文件名固定为 `assetId + 原文件扩展名`；反复“使用模板→保存覆盖”不累加前缀。旧模板仍从已存储的路径读取，使用后保存会写入稳定名称；图片字节、asset ID、组件引用与样式保持不变，不要求手工迁移原模板。

这些修复不改变上传步骤、账户缓存隔离、确认门槛及 Draft 回读要求。

## 模板提交与失败恢复

- 模板图片复制到暂存目录后，先发布到模板下的独立 `.revision-*` 目录，再通过同目录临时 JSON 文件的原子 rename 提交索引。索引切换是提交点；复制、图片目录 rename 或索引提交失败时，已保存模板的索引和图片保持可用，新建失败不发布模板。
- 旧图片版本只在索引成功提交后清理。清理失败不会把已成功保存或删除的模板报成失败；下次模板保存/删除会在跨进程锁内重试清理无引用版本、暂存目录及临时索引。旧路径格式兼容读取，旧格式目录在模板删除时一并清理。
- 锁释放先将 `.templates.lock` 原子改名为唯一的 `.templates-released-*` 目录，再尽力清理；改名失败时尝试直接移除。释放最多尝试 3 次、间隔 25ms，不重跑受保护操作。已释放目录清理失败留待后续模板操作处理，不改变成功回执或原始业务错误。
- 创建锁目录后若读取目录身份失败，尚未写入 owner 元数据或执行业务操作，立即同步移除本次创建的空目录并抛出原始错误。只使用空目录删除，不递归删除身份未知的内容；若权限等问题同时阻止清理，保留原错误并附停止全部编辑器后人工清锁的提示，不伪称自动恢复成功。
- 若锁持续无法释放，已提交操作仍返回真实结果，成功响应附 `warnings` 中的 `template-lock-release-pending`，界面同时显示恢复提示。同一服务在下次模板操作前核对设备、inode 和创建时间，只重试释放自己记录的残留锁；其他服务的锁不能被替换或删除。未成功执行的操作仍抛原始错误。
- 操作失败可在解除磁盘/权限问题后重试。突然退出遗留的 `.templates.lock` 仍遵循原规则：先停止全部编辑器，再移除残留锁；不按超时抢占锁。索引原子切换保证读者看到完整版本，不承诺断电时的磁盘持久性。

## 同草稿并发顺序

- 服务先收完整个请求体，再将同一草稿的读取、修改、确认、预览、模板保存及导出/上传按就绪顺序串行执行；每次操作读取最新草稿。慢请求不持有旧快照，不能覆盖另一字段的已保存修改或复活已删除组件。
- 导出/上传完成或失败后，队列继续处理后续修改；修改照常使确认失效。不同草稿不共用此队列。原有浏览器保存队列与输出前等待规则继续保留。
- 这不是跨客户端版本冲突提示：多个请求明确修改同一字段时，按服务端实际处理顺序以后者为准；排序索引也基于处理时的最新列表。普通草稿仍仅存在当前服务内存中。

## 回读节点关联

- 对普通邮件和 Outlook 分支分别比较按顺序提取的 URL 节点：链接目标及其文案、图片 src/Alt/所属链接、HTML 背景、inline CSS 图片，以及 VML 形状点击目标与填充图。图片和背景还绑定规范化内容分支、非空白正文位置范围及后代图片位置；相邻卡片文案相同、空表格单元格和 inline-block 卡片也参与归属区分。缺少节点、互换 URL、只剩前缀、目标与图片/文案错配或图片/背景跨块移动都不能报告回读成功。
- HTML/CSS 注释、data 属性、脚本/样式/模板中的字面字符串不能替代节点 URL。CSS 扫描先跳过完整引号字符串，`background-image: 'url(https://…)';` 不算图片，`background-image: url('https://…');` 仍可识别。CSS 按声明覆盖和 `!important` 处理；已经被后续背景声明覆盖的旧 URL 不算匹配。这是受支持邮件 HTML 的静态语义检查，不是浏览器完整 CSS 语法或计算样式验证。
- 保留单次实体解码、属性顺序/引号/大小写变化、无害单子节点包装和多 HTML 块回读的兼容；图片单独增加包装也可通过。表格单元格、行和分组的结束标签省略按当前嵌套表格作用域处理。布局表格的 background 仅在归属范围一致时可在 table/td 间归一化；不进行整个 DOM 或像素级相等比较，也不自动接受跟踪重写地址或新增图片节点。
- 有效 `display:inline` 优先于 div/p 等标签的默认块分类，局部包裹文案和图片不会凭空增加内容块；链接内此类包装的闭合不插入额外文案空格。注释、覆盖顺序和 `!important` 沿用共享 CSS 声明解析，真实 block/inline-block 卡片及跨块移动仍参与归属校验。

### 统一可见文字提取

- 正文、链接文案、图片/背景归属的位置由同一 `readback-html-tokens.mjs` 解析树提供，文本节点仅解码一次。普通邮件和 Outlook 条件分支分别解析并校验，不能拿另一分支或隐藏区域中的旧文案替代。
- 行内元素和 HTML 注释不添加空格：`Save<span>20%</span>` 与 `Save20%` 等价，与 `Save 20%` 不等价。源码真实空白可以折叠，但不能被标签凭空补回。默认块级元素（包括 center、address、article/section、列表描述项等）和 br 形成文字分隔；图片按既有回读契约作为可见分隔，Alt 单独校验，不计入正文。支持显式 inline/block 与当前表格结构，不依赖整个 DOM 相同。
- `script`、`style` 和 `title` 的内容只消费至各自结束标签，不计入正文或 URL 节点，内部的伪 HTML 不影响外层结构；`template` 支持嵌套。它们及 hidden、有效 display:none 子树的文字、链接和图片均不作为回读证据。HTML 非 void 元素尾部的 `/` 不会提前结束隐藏子树。
- 对省略 `</p>` 的回读，遇到新 p 或会结束段落的元素时，先闭合当前段落及其内层包装，再继承父级隐藏状态。查找不能跨越 template、表格/单元格或 button 等段落作用域边界；真实隐藏祖先仍隐藏。后续段落的文字、链接和图片不会被吞入前一段的隐藏子树。此兼容仅用于回读，不放宽待上传源码的安全校验。
- 若该隐式闭合会跨越尚未关闭的 a、b、strong 等格式化元素，HTML 可能重建这些元素，静态解析器不能确认其隐藏状态或链接归属，因此明确报 `unsupported implicit paragraph closure`，不返回验证成功；普通 span、已正确闭合的格式化标签和不可见 template 内部内容不受此限制。应检查远端结构，沿用只读恢复流程，不自动重复写入。title 只匹配完整标签名，允许识别带尾斜杠或属性的结束标签，避免吞掉后续正文。
- visibility:hidden/collapse 下的文字不计入正文；子元素显式 visibility:visible 可恢复显示，其继承的链接地址仍须校验。display:none 和 hidden 子树不能由子元素恢复。声明覆盖及 `!important` 使用同一 CSS 解析规则。
- title 起止标签使用 HTML ASCII 空白边界；NBSP 等字符不作为标签名分隔符。遇到实际结束标签候选但无法可靠分词（例如未加引号属性含 `<`）时，明确报 `unsupported ... closing tag`，不跳到更晚的结束标签并吞掉可见正文。支持范围内的带斜杠、带引号属性结束标签继续兼容。
- 非 template 区域中出现第二个尚未结束的 form 时，在段落闭合前报 `unsupported nested form`，避免把应被 HTML 忽略的开始标签当作解除隐藏状态的依据。form 状态不因普通栈弹出而丢失；独立表单及 template 内部内容不误判为嵌套。此规则不允许组件新增表单，待上传源码仍遵守既有安全白名单。
- 这是支持范围内的静态文字和节点校验，不计算完整样式表、尺寸裁切、遮挡、透明度或邮箱特有布局。输出源码、组件样式与上传步骤均不因此改写，真实收件箱视觉检查仍独立进行。
- `verify-existing` 仍只执行 GET；未解析本地资产必须在对应节点成为 Omnisend 图片 URL，并保持同一资产复用一致及原有新增不同图片数量约束。缺少上传映射时，它不能证明远程图片字节与本地文件相同，不将这个结果描述为图片内容比对。
- 回读校验失败不等于远端写入未发生；不自动再次写入、发送或排期，沿用现有只读恢复方式。
